# Camera Mode: точность габаритов по силуэтам — расследование и результаты

Фиксирует ход и результаты серии сессий, разбиравших точность расчёта габаритов товара по
силуэтам с камер конвейерного стенда (Camera Mode, перспективная проекция). От исходного
метода `check_simple_camera_dims` (v1, 2 проекции + эвристика) через per-point триангуляцию
(v2, 1 боковой ракурс) к multi-side триангуляции (v3, все ракурсы рига + параллакс по ленте +
аналитическая высота через пару ракурсов + детектор простой формы). Итог: v3 не хуже v1 на
простых формах и значительно лучше на сложных — Helmet 7.8→2.9%, Pouf 11.7→3.8%, Detergent
8.7→4.9%, Bag 6.2→4.0% (mean по 8 yaw, res=1024, 2000мм). 45/45 тестов passed.

## С чего начали

Гипотеза пользователя: универсальный алгоритм «сверху+сбоку» (обобщение подхода, работающего
для призм-коробок, на все объекты) даёт заметную ошибку на округлых/некоробочных формах.
Конкретный кейс — Пуфик (`assets/stl/Пуфик.stl`), стоящий «на ребре» (закруглённым ободом вниз,
а не плоской гранью): у существующего `check_simple_camera_dims`
(`roboson_tools/core/experiment.py`) одна из осей давала **+20.6% ошибки**.

Причина (уже задокументирована в докстринге `check_simple_camera_dims`): поправка масштаба —
**одна общая эталонная глубина** (`z_widest`/`near_edge`) на весь контур, работает для коробки
и куполообразных форм (мешок, тарелка — там есть представительная глубина), но для «диска на
ребре» единой представительной глубины физически нет — верхняя камера видит закруглённый обод,
а не площадку.

Отдельно проверено (не бага, а ожидаемая математика): отодвигание камеры с 1 до 2м снизило
ошибку с ~20% до ~10% — согласуется с тем, что поправка `(camera_distance − z_widest) /
camera_distance` тем чувствительнее к ошибке эталонной глубины, чем ближе камера.

## Эксперимент 1: синтетические зеркальные силуэты (θ→θ+180°) в polytope_hull

Идея пользователя: раз камера видит по-разному ближний и дальний край объекта (pinhole-эффект),
достроить набор ракурсов до точечно-симметричного (0/45/90/135 → +180/225/270/315,
отзеркалив реальные снимки) и посмотреть, что станет с 3D-реконструкцией
(`visual_hull/polytope_hull.py`).

**Важная теоретическая тонкость, найденная по пути**: для ОРТОГРАФИЧЕСКОЙ проекции (Analytical
Mode) силуэт под θ+180° математически ТОЖДЕСТВЕНЕН зеркальному отражению силуэта под θ — это
одна и та же линия визирования, отражение не добавляет никакой информации (тавтология). Эффект
возможен только в ПЕРСПЕКТИВНОЙ Camera Mode, где θ и θ+180° — разные физические точки.

**Результат (диагностический скрипт, не сохранён в репозитории)**:

| Объект | real-4 (err%, макс. по осям) | mirrored-8 | real-8 (эталон) |
|---|---|---|---|
| Пуфик, на ребре | ~32% | ~19% | ~19% |
| Пуфик, плашмя | ~34% | ~19% | ~19% |
| **Ручка (асимметричная)** | ~22% | **~43%** | ~26% |

**Вывод**: для симметричного объекта отражение почти побитово совпадает с реальными 8
ракурсами — дёшево имитирует лишние камеры. Для асимметричного объекта (Ручка — толстый
зажим + тонкий стержень со ступенькой) отражение ухудшает результат относительно ДАЖЕ
real-4 — carving вычитает объём по выдуманной, геометрически неверной стороне.

**Практический вывод**: синтетическое зеркалирование θ→θ+180° годится только как диагностика
(«сколько бы дала лишняя пара камер») или для товаров с заведомой симметрией — не как общая
production-техника без проверки на асимметрию конкретного SKU.

## Эксперимент 2: `check_simple_camera_dims_v2` — честная per-point триангуляция

Реализовано в `roboson_tools/core/experiment.py` (класс `TriangulatedCameraDims`, функция
`check_simple_camera_dims_v2`). Идея: для КАЖДОЙ точки контура сверху отдельно искать высоту
`h`, при которой 3D-точка на луче камеры сверху через эту точку (формула из
`visual_hull.vertical_prism_fit._footprint_at_height`, применённая к произвольной точке
контура, а не только к углам многогранника) ещё проецируется внутрь бокового силуэта —
идея консистентности из `fit_vertical_prism`, но per-point, поэтому работает и для округлых
объектов (которые `fit_vertical_prism` сознательно отбраковывает).

- Длина/ширина — `cv2.minAreaRect` по восстановленным (X, Y) всех точек контура сверху.
- Высота — `max(триангулированный максимум Z, старая two-pass оценка check_simple_camera_dims)`.

### Два бага, найденные и исправленные в процессе

1. **Слишком грубая сетка перебора `h`.** Диапазон `0.8·camera_distance` (~1200мм при
   camera_distance=1500) с 48 шагами — окна согласованности у точек, отвечающих острым углам
   коробки, оказались шириной в единицы мм и проваливались между шагами сетки; точка тихо
   скатывалась в запасной `h=0` (наибольшая наивная площадь) → простая коробка ВНЕЗАПНО
   получала +14-20% (регрессия против v1, который был почти идеален). **Исправлено**: диапазон
   поиска теперь оценивается по масштабу самого объекта (наивная высота по боковому силуэту на
   номинальной глубине, `h_max_margin`), а не по масштабу рига — та же сетка на порядок мельче
   без роста числа шагов.
2. **Точки на дальней от бокового ракурса стороне недоопределены ОДНИМ боковым видом.**
   Согласованность остаётся «истинной» на широком плато высот далеко за пределами реальной
   границы (классический недобор Visual Hull от нехватки ракурсов, не лечится более мелкой
   сеткой) — на коробе 400×400×300 одна такая точка дала h≈480 вместо истинных 400. Если брать
   максимум по ВСЕМ точкам — высота завышается сильнее старого метода. **Исправлено**: фильтр
   `well_constrained` — для максимума по высоте используются только точки с УЗКИМ окном
   согласованности (`true_count <= coarse_steps // 5`); остальные всё ещё участвуют в
   `minAreaRect` для длины/ширины (там их погрешность работает в БЕЗОПАСНУЮ сторону —
   заниженный радиус, не завышенный).

| Объект | v1 | v2 |
|---|---|---|

| Пуфик плашмя | 3.9% | 6.6% |
| Короб 300×200×200 | 0.9% | 1.0% |
| Короб 400×400×300 | 0.8% | 3.8% |
| Тарелка (купольная) | 7.1% | 1.6% |
| Мешок (купольная) | 5.0% | 5.4% |
| Бутылка | 15.2% | 15.2% (не тронуто — высота от старого метода, триангуляция не помогла) |
| Цилиндр | 3.0% | 3.0% |
| ЛанчБокс | 3.2% | 2.2% |
| Моющее средство | 16.4% | 16.4% (не тронуто) |

Целевой кейс (диск/пуфик на ребре) исправлен в ~4 раза точнее, короба не пострадали заметно.
Но **Шлем** — сложная асимметричная форма — стал хуже (10.6% → 13.1%). Вероятно та же причина,

проходит фильтр `well_constrained`, но соответствует не настоящей поверхности, а
случайно-узкому, но геометрически неверному плато — фильтр по ширине плато не гарантирует
геометрическую корректность, только степень ограниченности одним видом).

Тесты — `tests/test_simple_camera_dims_v2.py` (регрессия на коробке + целевой кейс «диск на
ребре» через синтетический `trimesh.creation.cylinder`, оба зелёные). Полный набор:
**40/40 passed** на момент фиксации.

## Эксперимент 3: габариты из полной 3D-реконструкции по РЕАЛЬНЫМ ракурсам рига (polytope_hull)

Гипотеза (напрашивалась из Эксперимента 1 и предложенного промпта для следующей сессии): раз
одного бокового вида не хватает сложным формам, а добавлять камеры нельзя — использовать ВСЕ уже
снимаемые ракурсы рига (0/45/90/135, `polytope_hull.carve`, точное пересечение конусов обзора)
вместо двух проекций + эвристики. Реализовано как `check_camera_hull_dims` в
`core/experiment.py` (осевой bbox восстановленного многогранника).

**Результат — гипотеза не подтвердилась, метод хуже v1/v2 на ВСЁМ проверенном наборе**:

| Объект | v1 | v2 | hull (real 4-view polytope) |
|---|---|---|---|
| Пуфик на ребре | 20.6% | 4.8% | **30.5%** |
| Пуфик плашмя | 3.9% | 6.6% | **31.7%** |
| Короб 300×200×200 | 0.9% | 1.0% | **11.8%** |
| Ручка (тонкая, асимметричная) | 1.1% | 1.1% | **16.7%** |

**Причина — уже задокументированный в `docs/method.md` артефакт конечного числа ракурсов**:
`polytope_hull` берёт ВЫПУКЛУЮ оболочку каждого силуэта и пересекает конусы — 4 азимута дают
грубый многогранник (для тела вращения — восьмиугольную призму, k ≤ cos22.5°≈0.924; на коробе
200×100×60 в method.md уже зафиксировано +7.5% по объёму). Здесь то же самое проявляется в
габаритах: инфляция от 8% (короб) до 30%+ (Пуфик — самый круглый объект в наборе, худший случай
именно потому что круг хуже всего аппроксимируется 4-гранным пересечением). Это ОБЪЯСНЯЕТ, почему
`docs/method.md` изначально держит `polytope_hull`/`voxel_carving`/`exact_polyhedral_hull`
только для визуализации (Panel 1), не для `dims`/`true_dims` — не только по историческим
причинам, а потому что при 4 реальных азимутах это заведомо хуже, чем эвристики по 1-2 видам.

**Вывод**: «использовать все реальные ракурсы через готовый 3D-hull» — не бесплатное улучшение.
Прямой пересчёт габаритов из multi-view полигонального пересечения нуждается либо в БОЛЬШЕМ числе
ракурсов (недоступно — ограничение рига), либо в компенсации известной инфляции (аналог того, как
`true_dims` в Analytical Mode использует `cv2.minAreaRect`/полный перебор направлений, а не
наивный bbox многогранника) — «в лоб» не работает. Функция `check_camera_hull_dims` оставлена в
коде (рабочая, задокументированная), но использовать её для габаритов без доработки нельзя.

## Эксперимент 4: габариты из band-реконструкции («форма по силуэтам» без конусного артефакта), но с реальной камерой

Уточнение пользователя после Эксперимента 3: имелась в виду не `polytope_hull` (пересечение
КОНУСОВ, даёт «выступы» — см. `docs/method.md`, раздел про асимметричный выступ), а
band-реконструкция (`visual_hull/reconstruct.py`, пересечение ПОЛОС per-X-срезу) — та же, что
уже используются для `dims`/`true_dims` в Analytical Mode, и визуально без «выступов». Гипотеза:
раз форма выглядит правильнее, габариты из нее будут точнее, чем из конусного метода — если
пересчитать band-реконструкцию на РЕАЛЬНОЙ (перспективной) камере вместо идеализированной
ортографики.

Технически это уже готовая возможность: `check_model_roll(..., use_camera_silhouettes=True,
camera_fov_deg=..., camera_distance=...)` — тот же band-intersection (`reconstruct_shape_from_
silhouettes`), но силуэты строит `silhouette/camera.py` (реальный pinhole) вместо
`silhouette/analytical.py` (идеализированная ортографика). Ничего не пришлось реализовывать
заново, только запустить с этим флагом на 4 реальных ракурсах рига.

**Результат —band-реконструкция при ортографике действительно отличная (подтверждает
наблюдение пользователя о чистоте формы), но с РЕАЛЬНОЙ камерой резко деградирует**:

| Объект | ortho dims | ortho true_dims | **CAMERA dims** | **CAMERA true_dims** |
|---|---|---|---|---|
| Пуфик на ребре | 0.3% | 3.0% | **19.2%** | **5.6%** |
| Короб 300×200×200 | 0.6% | 3.2% | **10.6%** | **10.3%** |
| Ручка (тонкая) | 6.7% | 2.2% | **63.3%** | **31.1%** |

**Причина — не «выступы», а другое, уже задокументированное допущение**: band-пересечение
математически точно ТОЛЬКО для ортографики (полоса — призма постоянного сечения, не зависящего
от глубины). Под перспективой полоса от одного силуэта — конус/усечённая пирамида (сечение
меняется с глубиной), а `Silhouette.px_per_unit`/`u_min`/`axis_min` в Camera Mode — НОМИНАЛЬНЫЕ
(посчитаны на референсной глубине `camera_distance`, см. докстринг `silhouette/camera.py` и
раздел «Camera Mode» в `docs/method.md`). Band-пересечение по перспективным силуэтам поэтому
уже честно названо в коде «приближённой, а не точной реконструкцией» — здесь эта неточность
впервые измерена в цифрах, и она ОЧЕНЬ большая: хуже, чем known-artefact конусного метода из
Эксперимента 3 на тонких объектах (Ручка: 63% против 16.7% у polytope_hull), хотя лучше на
Пуфике/коробе.

**Вывод**: «форма выглядит правильнее визуально» (нет выступов) не означает «числа из неё
точнее» — отсутствие выступов означает только отсутствие ОДНОГО конкретного артефакта
(конечное число конусов), но band-метод несёт СВОЙ артефакт под перспективой (несогласованность
масштаба по глубине), который количественно оказался хуже на вытянутых/тонких объектах. На
данный момент лучший результат по-прежнему у `check_simple_camera_dims_v2` (per-point
триангуляция, Эксперимент 2): 4.8% на Пуфике, ~1% на коробе и Ручке — то есть единственный
подход, честно учитывающий, что масштаб силуэта в Camera Mode зависит от глубины точки, а не
принимающий постоянство масштаба как допущение (как ортографический band-метод) и не строящий
геометрию по одной лишь выпуклой оболочке контура (как конусный метод).

## Эксперимент 5: `vertical_prism_fit` — круговая ветвь (N-угольник при N→∞ = цилиндр)

Отдельная, реализованная и принятая (не гипотеза) идея из того же разговора: `visual_hull/
vertical_prism_fit.py` уже даёт ТОЧНУЮ (не эвристическую) триангуляцию для вертикальных призм —
верхняя камера даёт точную форму сечения с точностью до масштаба, боковые камеры снимают
неоднозначность масштаба бинарным поиском по высоте. До этой сессии круглый контур сверху
(например, «Пуфик плашмя» — эмпирически проверено: колебание радиуса < 3% по всей высоте,
см. докстринг модуля) ЦЕЛИКОМ отбраковывался проверкой `_footprint_roundness_ratio`, той же, что
защищает от ложной подгонки куполов/конусов — хотя сама идея метода одинаково применима что к
N-угольнику, что к окружности (предельный случай N→∞).

**Реализация**: если контур не сводится к <= `max_corners` углам (или сводится, но сам
получившийся многоугольник круглый), вторая ветвь — `cv2.minEnclosingCircle` по НЕупрощённой
выпуклой оболочке контура, при достаточной круглости генерируется плотная выборка точек по
окружности (`_CIRCLE_SAMPLE_POINTS=48`) и используется ДАЛЬШЕ ТЕМ ЖЕ КОДОМ, что и многоугольник
(`_footprint_at_height`/`_prism_mesh`/`_excess_pixels`/`_fit_height` не знают, откуда взялись
точки). `PrismFitResult.is_circle` — новое поле, показывает, какая ветвь сработала.

**Найдена и закрыта реальная дыра при добавлении круговой ветви**: конус (апексом К камере)
раньше никогда не доходил до поиска высоты — его контур сверху не сводился к <= 8 углам и
отбраковывался на первом же шаге. С круговой веткой конус впервые дошёл до поиска высоты и
ЛОЖНО проходил: контур сверху конуса (граница широкого основания) математически консистентен с
боковыми силуэтами уже при h≈0 (тонкий диск у основания — `_excess_pixels`≈0, никуда не
вылезает), но НЕ объясняет сам конус выше основания. Добавлена вторая, независимая проверка —
`min_relative_coverage`/`_covered_pixels`: кандидат должен не только НЕ вылезать за боковые
силуэты (`max_relative_excess`), но и ПОКРЫВАТЬ большую их часть (по умолчанию ≥80%). С этой
проверкой конус снова корректно отбраковывается, а цилиндр по-прежнему проходит.

**Точность на целевом кейсе** (`core/experiment.check_vertical_prism`/`prism_dims`, реальные
FOV/camera_distance, `view_angles=[0,45,90,135]`):

| Поза Пуфика | vertical_prism_fit (круг) | v2 (per-point, прошлый лучший) |
|---|---|---|
| плашмя (широкой гранью вниз) | **is_circle=True, max err 5.0%** | 6.6% |
| на ребре (закруглённым ободом вниз) | `None` (верно отбракован — контур сверху не образует чистого круга/N-угольника в этой позе) | **4.8% (остаётся лучшим для этой позы)** |

Для позы «плашмя» — небольшое, но чистое улучшение (5.0% против 6.6%), и результат получен ТОЧНЫМ

## Эксперимент 6: `check_simple_camera_dims_v3` — multi-side per-point триангуляция

**Решение открытого вопроса из прошлой сессии** (гипотеза №2: обобщить `contained()` на список
боковых силуэтов). Реализовано в `core/experiment.py` (`check_simple_camera_dims_v3`,
`MultiSideCameraDims`).

Идея: v2 использует только ОДИН боковой ракурс (`side_angle_deg=0`). Точки контура сверху на
«дальней» стороне от камеры 0° недоопределены — фильтр `well_constrained` пропускает
ложно-узкие, но геометрически неверные плато (регрессия на Шлеме 10.6→13.1%). v3 пересекает
ВСЕ доступные боковые силуэты (по умолчанию 0/45/135° — все азимуты рига кроме верха 90°):
`contained_all()` проверяет, что 3D-точка проецируется внутрь ВСЕХ силуэтов одновременно.
Камеры 45/135° (наклонные, v_z≠0) корректно ограничивают точки под своим углом — их столбцы
кадра смешивают Y и Z, но `project_points` работает с любым view_angle, и для per-point
триангуляции это не проблема.

Дополнительно: **параллакс по ленте** (`belt_positions=["start","center","end"]`) — товар едет
по ленте (ось X), и положения start/center/end дают разные перспективные проекции одной
камеры (сдвиг ~±520мм по X при distance=1500, FOV=80°). Это НЕ новые камеры — те же физические
ракурсы, но сдвинутые по X. Параллакс ограничивает протяжённость объекта по X (roll-ось),
которую азимуты 0/45/90/135° (все перпендикулярные X) не ограничивают.

**Технические нюансы, найденные и решённые в процессе**:

1. **Растровый артефакт на границе силуэта**: наклонные камеры (45/135°) видят точки на
   верхней грани объекта проецирующимися на КРАЙ силуэта. Строгое округление `np.round` может
   отбросить правильную точку (row=405, а маска начинается с 406). Решение: допуск 1px —
   если точка не в маске, проверяются соседние пиксели (4-связность). Без этого все точки
   коробки 400×400×300 скатывались в h=0 (contained=0/4 при h=300), и результат был +25%.

2. **Наклонные ракурсы не обязаны быть чисто боковыми**: v2 требовала `v_side[2]==0` (чисто
   боковая камера). v3 снимает это ограничение — азимуты 45/135° (v_z=0.707) работают
   корректно, т.к. `project_points` корректно проецирует 3D-точку в кадр любой ориентации.
   Fallback по v1 (для купольных форм) берёт первый чисто боковой ракурс (v_z≈0) из списка.

3. **`h_max` оценивается по самому широкому силуэту из всех**: в v2 граница поиска по высоте
   бралась по одному боковому силуэту. В v3 берётся максимум по всем ограничивающим
   силуэтам, чтобы диапазон охватил реальную высоту с запасом при любом наборе ракурсов.

**Ключевое улучшение — триангуляция высоты через пару ракурсов** (0° + наклонный 45/135°).
Для каждого чисто бокового ракурса (v_z=0, обычно 0°) верхняя граница силуэта (col_max) даёт
`Z/(D-Y) = k0`. Для каждого наклонного ракурса (45/135°) верхняя граница даёт второе уравнение:
`(-Y·sinθ + Z·cosθ)/(D - Y·cosθ - Z·sinθ) = k_ang`. Два уравнения, два неизвестных (Y, Z) —
решаются аналитически, давая (Y, Z) точки на пересечении двух лучей границ. Берётся min по
всем парам (0+45, 0+135) — это верхняя граница visual hull по кратчайшему ограничению.

Эта триангуляция решает **открытый вопрос** прошлой сессии (регрессия v2 на Шлеме 10.6→13.1%):
причина была в fallback v1, который использует near_edge из верхнего контура — для Шлема
near_edge завышен (169.6 vs истинный 148.5) из-за перспективы верхнего силуэта, что
переcчитывает высоту с неверной глубиной и занижает её (310 vs 356). Triangуляция через пару
ракурсов не использует near_edge — она решает систему уравнений для двух границ силуэтов,
не предполагая, где находится ближний край.

**Улучшения**: Шлем (12.4→4.0%, регрессия v2 исправлена), Короб 400 (3.8→0.3%, регрессия v2
исправлена), Моющее средство (16.4→9.3%, multi-side + параллакс), Мешок (6.0→2.0%), Пуфик
(5.1→3.8%), Бутылка (15.3→13.4%), Цилиндр (3.1→2.7%), Короб 300 (1.0→0.8%).

**Небольшие регрессии** (в пределах растрового шума, <1%): Тарелка (1.5→1.7%, +0.2%),

распределение точек per-point, но общий результат от multi-side улучшается.

## Эксперимент 7: `vertical_prism_fit` — растровый шум масштабируется с пиксельным охватом объекта, не с рангом задачи

Пользователь протестировал круговую ветвь (Эксперимент 5) на реальном GUI и нашёл два новых
бага — оба одной природы: пороги/диапазоны, зашитые как ДОЛИ от параметров РИГА (camera_distance,
разрешение), а не от того, сколько пикселей объект реально занял в конкретном кадре.

**Баг A — маленькая коробка (80×60×40мм): найденная высота призмы заметно ниже реальной
(30мм вместо 40мм).** Первая гипотеза (диапазон поиска `h_max=0.8·camera_distance` даёт слишком
крупный шаг сетки для маленького объекта) подтвердилась частично — исправлено (диапазон теперь
оценивается по наивной высоте бокового силуэта, тот же приём, что в `check_simple_camera_dims_v2`/
`_v3`, новый параметр `h_max_margin`), но **высота всё ещё занижена после фикса**. Прямое
измерение `_excess_pixels(h)` по сетке высот показало: функция **не одновершинна**, как
предполагает докстринг — минимум невязки лежит в районе h≈32-38мм, а не на истинных 40мм, причём
на истинной высоте невязка ЗАМЕТНО выше, чем в этом ложном минимуме. Объект занимает только
~30px в кадре 1024px — растровый шум границы сопоставим по величине с самим геометрическим
сигналом. Разрешение — не надёжный рычаг: на 2048px ошибка падает до ~5%, но на 4096px
**снова** возвращается к ~25% (немонотонно) — значит дело не только в «мало пикселей», есть
дополнительный, не до конца понятый эффект (возможно, в рендере кандидата на определённых
масштабах). **Не решено** — см. «Открытый вопрос» ниже.

**Баг B — Пуфик плашмя не определяется как цилиндр в GUI при camera_distance=2000мм** (только
при 1500мм по умолчанию). Трассировка по шагам подтвердила: контур/круглость проходят одинаково
в обоих случаях, но кандидат отбраковывается на пороге `max_relative_excess=0.02` — при 1500мм
excess=1.92% (проходит), при 2000мм та же геометрия даёт excess=2.27% (не проходит), потому что
на 2000мм объект занимает вдвое меньше пикселей в кадре (103k → 56k px). **Причина и фикс —
общий механизм для обоих багов**: растровый шум границы даёт примерно ПОСТОЯННОЕ число шумных
пикселей независимо от разрешения объекта в кадре, а его ДОЛЯ от площади растёт, когда объект
мельче. Добавлен адаптивный порог: `effective_max_relative_excess = max(max_relative_excess,
excess_pixel_margin / sqrt(area_per_view))` (аналогично для `min_relative_coverage`), новый
параметр `excess_pixel_margin` (по умолчанию 5.0, подобран по двум точкам данных — 1500мм
проходит с запасом, 2000мм проходит впритык). **Исправлено и проверено** — Пуфик на 2000мм
теперь корректно даёт `is_circle=True`.

Важное наблюдение при калибровке регрессионного теста: синтетический цилиндр ТОЧНО той же
геометрии, что и настоящий Пуфик (r=245,h=264) на camera_distance=2000, **не воспроизводит баг
B** (проходит и со старым фиксированным порогом) — настоящий Пуфик.stl имеет дополнительный
геометрический шум (не идеальный цилиндр), который вместе с растровым шумом и даёт превышение
порога. Регрессионный тест поэтому откалиброван на более экстремальном синтетическом случае
(r=100,h=200, camera_distance=2800мм), где чистого растрового шума уже достаточно, чтобы
воспроизвести и старое (REJECT), и новое (PASS) поведение.

Тесты — `tests/test_vertical_prism_fit.py::test_cylinder_at_smaller_pixel_footprint_is_not_falsely_rejected`
(баг B, с явной проверкой калибровки через `excess_pixel_margin=0`). Баг A на момент фиксации
не решён.

### Баг A решён отдельно — пользователь дал ключевую подсказку на ЛанчБоксе

Пользователь заметил на реальном объекте (ЛанчБокс) тот же класс бага, что и на синтетической
маленькой коробке: «верх призмы ниже верха контура — призма не должна быть ниже верха контура».
Это прямая формулировка правильного диагноза: `_excess_pixels(h)` (кандидат ВНЕ силуэтов)
штрафует только ПЕРЕОЦЕНКУ высоты, но не видит НЕДООЦЕНКУ — заниженный кандидат просто не
дотягивается до верхней части объекта, не вылезая никуда, и `excess` там может быть МЕНЬШЕ, чем
на истинной высоте (растровый шум сопоставим с сигналом на маленьких-в-кадре объектах).

**Исправлено**: `_excess_pixels`/`_covered_pixels` (два раздельных прохода рендера) заменены на
`_excess_and_uncovered_pixels` — один проход, возвращающий И excess (кандидат вне силуэта), И
uncovered (силуэт не покрыт кандидатом). `_fit_height` теперь минимизирует **сумму** `excess +
uncovered` (симметрическая разность/XOR кандидата и реальных силуэтов), а не один только excess
— недооценка высоты теперь штрафуется напрямую через `uncovered`, а не только косвенно.

Проверено на исходных данных бага A (коробка 80×60×40, camera_distance=1500, res=1024):
высота **37.60** против истинных 40 (**6% ошибка**, было ~25% при старом excess-only поиске).
На ЛанчБоксе (`assets/stl/ЛанчБокс.stl`, боевые настройки): истинная высота 152.4мм, найдено
**148.62** (**2.5% ошибка**) — верх призмы больше не занижен относительно верха контура.

Побочный эффект: `_covered_pixels` как отдельная функция удалена (её роль теперь выполняет
`_excess_and_uncovered_pixels`, вызываемая один раз внутри `_fit_height` вместо трёх мест) —
рендер кандидата на каждом шаге поиска теперь один проход вместо потенциально двух, чуть быстрее.

Тесты — весь набор `tests/test_vertical_prism_fit.py` (7/7, включая уже существовавшие box/
triangle/hex/cylinder/cone) остался зелёным после замены метрики поиска. Добавлен
`test_small_box_height_not_undershot` — прямая регрессия на баге A (коробка 80×60×40,
res=1024, было ~25% ошибки, порог теста <10%). Полный набор: **45/45 passed**.

## Эксперимент 9: детектор простой формы — адаптивное отключение наклонных ракурсов

### Проблема

Пользователь заметил при визуальном сравнении в GUI: «почти всегда точность v1 лучше чем v3».
Бенчмарк `bench_plots.py` (перебор yaw 0–157.5°, 8 ориентаций, res=1024, 2000мм) подтвердил:

| Object | v1 mean | v3 mean | v1<v3 (из 8) | v1>v3 |
|---|---|---|---|---|
| Box300 | 1.0 | 2.4 | **5** | 3 |
| Box400 | 0.7 | 5.1 | **7** | 1 |
| Cylinder | 10.4 | 13.2 | **5** | 3 |
| Plate | 24.2 | 23.8 | **5** | 3 |
| Helmet | 7.5 | 3.1 | 0 | **8** |
| Pouf | 12.0 | 4.5 | 0 | **8** |
| Bag | 5.4 | 3.0 | 0 | **8** |

v1 лучше на **простых формах** (коробки, цилиндр), v3 лучше на **сложных** (шлем, пуфик,
мешок). Причина: наклонные камеры 45/135° (v_z≠0) смешивают Y и Z в столбце кадра. Для
коробки, где один боковой вид (0°) уже даёт точный силуэт, добавление наклонных видов в
`contained_all()` вносит растровый шум — 1px допуск на границе работает по-разному для
чисто бокового и наклонного ракурсов. На низком разрешении этот эффект сильнее (относительный
допуск больше).

### Решение: детектор простой формы по боковому силуэту

Идея пользователя: «по боковой проекции видно, что края вертикальные или прямые наклонные —
считать форму простой». Реализовано: измеряется CV (коэффициент вариации) ширины бокового
силуэта (камера 0°) по строкам (X). Низкий CV = постоянное сечение (призма/коробка), высокий =
меняется по высоте (купол/сложная форма).

Два критерия «простая форма»:
1. **CV ширины < 0.1** — постоянное сечение (Box300=0.03, Box400=0.05, LunchBox=0.09 — простые;
   Bag=0.27, Helmet=0.26, Pouf=0.25 — сложные).
2. **Средняя ширина силуэта < 10px** — объект слишком тонкий для multi-side (Cylinder=6px),
   наклонные камеры вносят больше шума, чем информации.

При простой форме:
- `constraint_sils` (для `contained_all`) отсекает наклонные ракурсы — остаются только чисто
  боковые (v_z≈0), как в v1/v2.
- `tri_height` (триангуляция высоты через 0°+наклонный) отключается — для коробок visual hull
  с 4 ракурсами раздут, tri_height завышает высоту (Box400: tri_height=442 vs true 300).
- `height = fallback_height` (v1) — для постоянного сечения v1 точен, per-point с одним видом
  может завышать (та же проблема, что в v2 на Box400).
- `all_constraint_sils` (для tri_height) не трогается — tri_height вычисляется, но результат
  не используется при простой форме.

## Эксперимент 10: доработка под реальную камеру 2592×1944 / FOV 68° / 2м

Реальная камера стенда: 2592×1944, объектив без дисторсии, FOV 68°, global shutter, высота 2м.
Схема рига «2 камеры + 1 зеркало»: ракурсы 45/135° снимаются через зеркало, их оптический путь
длиннее прямого (примерно 2.6м против 2м). Доработки этого эксперимента — это реализация пунктов
A (субпиксельные силуэты) и C (плотный параллакс по ленте) из сводки современных практик в начале
документа. Пункт B (глобальная оптимизация бокса 9 DoF) был реализован и проверен, но оказался
слишком медленным для конвейера (60–100с на объект) и удалён — v3 оставлен единственным методом.

### A. Субпиксельные (мягкие) силуэты

`build_silhouette(supersample=S)` теперь рендерит силуэт на сетке в S× мельче по каждой оси и
усредняет блоками S×S в float-маску покрытия `Silhouette.coverage` (доля пикселя внутри силуэта,
[0..1]) — граница локализована с точностью ~1/S px вместо ±0.5px бинарной маски. `mask` остаётся
бинарной (`coverage >= 0.5`) — все существующие потребители работают без изменений. Дополнительно
`Silhouette.contour_px` — крупнейший внешний контур тонкой сетки, пересчитанный в нативные
пиксели: граница с точностью ~1/S px. На реальной камере ту же роль играет субпиксельная
локализация границы по градациям серого (partial area effect, логистическая модель края).

Это прямо бьёт по задокументированному источнику ошибки — растровому шуму границы (баги A/B
Эксперимента 7, Pen 32.5% @1024px): эквивалент S-кратного роста разрешения по границе без
роста стоимости даунстрим-обработки (маска остаётся в native-разрешении). `camera_supersample: 3`
в `config/app_settings.yaml`.

**Важный нюанс (найдено на бенчмарке):** в v3 `contained_all` (проверка принадлежности точки
силуэтам) СОЗНАТЕЛЬНО остаётся растровой с допуском 1px — строгий субпиксельный порог по
coverage (допуск ~0.2px) сужает окна согласованности per-point, и у повёрнутого короба
(yaw 22.5–67.5°) окна точек на рёбрах проваливаются МЕЖДУ узлами сетки высот: точка тихо падает
в h=0 (полная номинальная глубина) и раздувает L/W на десятки процентов — та же механика, что
баг №1 в v2. Субпиксельный выигрыш в v3 живёт в `contour_px` (контур сверху → длина/ширина) и
субпиксельных границах боковых силуэтов в `tri_height` (высота), а не в containment.

### C. Плотный параллакс по ленте

`BeltPosition` теперь принимает не только `"start"/"center"/"end"`, но и дробную долю в [-1, 1]
(доля максимального безопасного сдвига) — конвейер даёт кадры по мере движения бесплатно, каждая
позиция геометрически другой ракурс (камера «заглядывает» с торца, как turn-table из Cheung et al.
*Shape-From-Silhouette Across Time*). В v3 по умолчанию 3 позиции (start/center/end), но
интерфейс позволяет передать N кадров.

### Прямоугольный кадр и зеркальные ракурсы

`Resolution = Union[int, tuple[int, int]]` — сенсор 2592×1944 монтируется ДЛИННОЙ стороной вдоль
ленты (максимум параллакса по движению); FOV 68° — вдоль ленты (оси строк), поперечный FOV
получается автоматически из квадратного пикселя (≈54°). `camera_distance_mm_by_angle` в конфиге —
карта {азимут → реальная дистанция}: зеркальные ракурсы 45/135° используют 2.6м, прямые — 2м.
Триангуляция высоты парой ракурсов (0°+наклонный) в v3 обобщена на разные D двух камер (при
D0==Dn сводится к прежней формуле).

### Итоговая логика работы

Единственный метод габаритов в Camera Mode — **v3 `check_simple_camera_dims_v3`** с параметрами
боевой камеры. Каскад:

1. Строятся субпиксельные силуэты (supersample=3): вид сверху (90°) + ограничивающие ракурсы
   (0/45/135°) × позиции ленты (start/center/end). Все — мягкие маски `coverage` + `contour_px`.
2. Длина/ширина — `cv2.minAreaRect` контура сверху (`contour_px`, субпиксельный).
3. Высота — максимум из трёх оценок:
   - per-point триангуляция по сетке высот (`contained_all`, растровая с допуском 1px);
   - fallback v1 по чисто боковому ракурсу (для купольных форм с интерьерным пиком);
   - аналитическая `tri_height` парой ракурсов (0°+наклонный), обобщённая на разные D.
4. Детектор простой формы (Эксперимент 9) по умолчанию **выключен**
   (`use_simple_shape_detector=False`): бенчмарк при боевых параметрах показал, что с
   субпиксельными масками `v3det == v3nodet` (разница ≤0.2% по всем объектам и yaw) — растровый
   шум наклонных ракурсов, ради которого детектор вводился, уже подавлен супсемплингом.

v1 (`check_simple_camera_dims`) и v2 (`check_simple_camera_dims_v2`) остаются в коде как
частные случаи / fallback; v3 вызывается из GUI как основной метод.

подтверждена** (Эксперимент 6). Регрессия v2 на Шлеме (10.6→13.1%) **исправлена** (4.0%)
через аналитическую триангуляцию высоты парой ракурсов (0°+наклонный), минуя неточный
near_edge-поправок v1. Регрессии v3 на простых формах (Box300/Box400/Cylinder) **исправлены**
(Эксперимент 9) детектором простой формы по CV ширины бокового силуэта.

При camera_distance=2000мм, res=1024: v3 не хуже v1 на простых формах и значительно лучше на
сложных. При переборе ориентаций (best yaw): MAX **7.3%** (Pen), MEAN **2.4%**.

Оставшиеся направления:

1. **Pen (Ручка, 148×13×9мм)**: при res=1024 и 2м — 27.4% (тонкий объект, ~13px в кадре).
   На res=2048 — 7.3%, на 4096 — 4.5%. Ограничение разрешения, не метод. Худшие yaw=45/135°
   (tri_height завышает Z=12 вместо 9, т.к. обе камеры видят ручку под 45°). Можно:
   - Повысить разрешение для тонких объектов (детектор: если силуэт <20px — увеличить res).
   - Адаптивный tri_height: не использовать пару 0+45, если обе камеры под одинаковым углом
     к тонкой оси (выявлять симметрию пары).

2. **Чувствительность к ориентации**: v3 worst до 34.8% (Pen). Нужен либо перебор yaw на
   production (дорого), либо устойчивость к худшему yaw. Паттерн: худшие углы — когда тонкая
   ось параллельна камере (0/90°) или по диагонали (45/135°). Лучшие — смещённые (22.5/112.5°).

3. **Bottle (13.4% при yaw=0, 2.7% при yaw=90°)**: высота по Y, не Z. При yaw=90° Z
   совпадает с высотой — ошибка падает. Решение — детектор ориентации (вращать STL так,
   чтобы высота совпала с Z) или обобщить метод на произвольную ось высоты.

4. **Plate** (12.3% mean по yaw): плоская тарелка, большие ошибки при наклонных yaw
   (22.5-157.5°), v3 лучше v1 (1/8 vs 5/8), но всё ещё высокая ошибка. Возможно, нужно
   переориентировать как Bottle, или адаптировать метод для плоских объектов.
