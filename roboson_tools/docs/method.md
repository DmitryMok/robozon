# Метод: габариты по силуэтам и «круглая проекция» (потенциал к перекату)

Документ описывает, как стенд `roboson_tools` вычисляет по набору силуэтов:

1. **габариты объекта**;
2. **признак «объект может катиться»** — через поиск круглой проекции.

Оба расчёта используют только силуэты (бинарные маски с известным масштабом) — то же,
что реальная CV-система получит с кольца камер/зеркал вокруг конвейера. Меш объекта
в расчётах не участвует и служит лишь для генерации силуэтов и контроля точности.

## Исходные данные

Объект движется по конвейеру вдоль продольной оси **X**. Направления наблюдения
(`view_angles`) — азимуты **θ** вокруг оси X в поперечной плоскости Y–Z
(конфигурация по умолчанию: 0°, 45°, 90°, 135° — «2 камеры + зеркало»).
Для каждого θ строится ортографический силуэт: строка растра однозначно соответствует
позиции по X, столбец — поперечной координате u вдоль оси r<sub>θ</sub> = (0, −sin θ, cos θ).
Все силуэты набора растеризуются с **единым масштабом** (общий extent → одинаковый
px_per_unit), поэтому они сравнимы между собой напрямую.

## Реконструкция формы по силуэтам (Visual Hull)

Сечение объекта в позиции x восстанавливается пересечением «полос» (bands):
каждый силуэт в строке, соответствующей x, даёт интервал [u₁, u₂] — полосу
допустимых положений в плоскости Y–Z; пересечение полос от всех углов —
выпуклый многоугольник сечения S(x).

Полная форма — стопка из N сечений (по умолчанию N = 50) на равных шагах по занятой
длине X. Это верхняя оценка объекта: Visual Hull всегда **содержит** объект, поэтому
все метрики ниже — консервативные (в сторону «больше/круглее»).

## Габариты по силуэтам

- **X**: пересечение диапазонов занятых строк всех силуэтов (каждый силуэт — экструзия,
  содержащая объект, значит объект лежит в пересечении их X-диапазонов).
- **Y, Z**: объединение bounding box всех восстановленных сечений S(x).

Габариты считаются в текущей ориентации объекта (оси конвейера) — как их измерила бы
реальная система. Точность на тестовых мешах ~0.1–0.5 % (погрешность растеризации
и конечного числа сечений); GUI показывает рядом истинные габариты меша для контроля.

**Осевой bbox в текущей ориентации растёт при повороте на произвольный угол** — это не
артефакт реконструкции, а неизбежная геометрия: развёрнутый на 22.5° короб 300×200×200 даёт
bbox ~351×296×200 (диагональ вместо стороны), хотя сам короб не изменился. Для сортировки по
размерной категории такое поведение неприемлемо — нужны габариты объекта, не зависящие от
того, как он лёг на ленту.

### Истинные (минимальные) габариты — `check_model_roll.true_dims`

`check_model_roll` дополнительно ищет **минимальный охватывающий бокс** восстановленной по
силуэтам формы — тем же перебором направлений по полусфере, что и для круглой проекции (общее
облако точек, свой оптимум для каждой метрики): для каждого направления d толщина вдоль d
считается точно (max−min проекции), а стороны прямоугольника в перпендикулярной плоскости —
через `cv2.minAreaRect` (точное решение 2D-подзадачи). Направление с минимальным объёмом
d·сторона1·сторона2 — приближение к минимальному 3D-боксу (полный перебор SO(3) избыточен;
этого сокращённого перебора достаточно для box-подобных объектов, которые и мотивировали
метрику). Результат — тройка размеров (по убыванию), не зависящая от Roll/Pitch/Yaw:
на короб 300×200×200 при развороте 0/22.5/45° разница с истиной остаётся < 5%, тогда как
осевой bbox выше при 22.5° уже даёт +17% по X. Показывается в GUI (Panel 4, «Истинные
габариты») и CLI (`roboson_tools.cli check` → `true_dims`).

Для правил постановки (10×10×10 … 450×320×320 мм) сравнивать следует именно `true_dims`
(отсортированные тройки размеров), а не осевой `dims` в текущей ориентации.

## Почему «круглое сечение» — не тот критерий

Старый алгоритм искал круглое **сечение** перпендикулярно X (с перебором Yaw).
Это решает не ту задачу:

- **Ложные срабатывания.** Наклонное сечение конуса — окружность (теорема Данделя о
  конических сечениях): при переборе Yaw алгоритм находил «круглое сечение» на скосе
  горлышка бутылки — математически корректный, но физически бессмысленный результат.
  Любая коническая фаска у некруглого предмета давала бы такой же ложный круг.
- **Пропуски.** У цилиндра, стоящего вертикально, все сечения поперёк X —
  прямоугольники: ни одного круглого сечения, хотя объект очевидно может катиться.

Физический смысл категории «требует доупаковки» — предмет **может покатиться** на
ленте/лотке. Перекат — это вращение вокруг оси, и определяется он проекцией, а не
отдельным сечением.

## Критерий «круглая проекция»

Объект может катиться вокруг оси **d**, если при вращении вокруг d его наибольший
радиус контакта почти не меняется. Максимальный радиус объекта в каждом направлении
поперёк d — это в точности граница **выпуклой оболочки ортографической проекции**
объекта вдоль d. Значит:

> Объект имеет потенциал к перекату ⇔ существует направление d, для которого
> проекция объекта вдоль d близка к кругу:
> **k = R<sub>впис</sub> / R<sub>опис</sub> ≥ 0.8** (порог из постановки задачи).

Примеры: у лежащего цилиндра и бутылки круглая проекция — вдоль их оси; у шара — любая;
у коробки круглой проекции нет ни в одном направлении.

### Алгоритм — G4 (рабочий метод, `core/experiment.check_model_roll_g4`)

Старый алгоритм «перебор полусферы с шагом 5°» (`check_model_roll`, ~1.5 с на объект)
заменён на **G4** — гибрид PCA-подхода с локальным поиском для пограничных случаев.
Причины: (а) 1.5 с не укладывается в бюджет конвейера (<0.5 с); (б) SCAN давал ложные
срабатывания на почти-кубе и гранёном цилиндре. G4 решает обе проблемы: 17–148 мс на
объект, 0 ложных «катится» для некруглых, 0 пропусков катающихся в основной
сортировщик. `check_model_roll` оставлен как эталон-оракул для валидации на новых
объектах; `check_model_roll_pca`/`check_model_roll_f1` — как диагностические.

**Идея G4.** Тело качения симметрично относительно своей оси → ось качения обычно
совпадает с одной из 3 главных осей инерции (PCA). Но у асимметричных катящихся
объектов (шлем с козырьком, цилиндр с боковым грузом) ось качения косая — не совпадает
с PCA-осями. G4 покрывает это расширением множества кандидатов и локальным поиском
для пограничных случаев.

**Алгоритм:**

1. Восстановить форму по силуэтам (стопка сечений, см. выше); вершины контуров сечений
   образуют облако 3D-точек формы.
2. PCA → 3 главные оси инерции + 3 собственные значения дисперсии σ_i.
3. Базовые 6 кандидатов: 3 PCA-оси + 3 диагонали между парами PCA-осей (нормированные
   суммы). Диагонали добавлены для «косой оси качения» (шлем: k=0.858 на PCA0+PCA2 vs
   0.783 на чистой PCA0).
4. Для каждого кандидата: спроецировать облако точек на плоскость ⊥ d, взять
   **выпуклую оболочку** проекции и посчитать k = R<sub>впис</sub>/R<sub>опис</sub>
   (R<sub>опис</sub> — `cv2.minEnclosingCircle` по вершинам, R<sub>впис</sub> — максимум
   `cv2.distanceTransform` растеризованного многоугольника). Взять max → `k_base`,
   лучшее направление `d_base`.
5. **Трёхкатегорный вердикт:**
   - `k_base ≥ 0.8` → **round** (катится) — без fallback.
   - `k_base < 0.65` → **not_round** (явно не катится) — без fallback.
   - `k_base ∈ [0.65, 0.8)` → **зона неуверенности**: запускается локальный поиск
     вокруг `d_base` (сетка азимут/подъём, радиус 20°, шаг 5°, ~81 направление).
     Если локальный поиск нашёл k ≥ 0.8 → **round**. Иначе → **uncertain**
     (требует перепроверки оператором / ручным потоком).
6. Найденная ось показывается на 3D-виде, проекция с окружностями — в Panel 3.

**Три категории вместо двух** — реализация логики пользователя «лучше ошибиться в
сторону круглого, чем пропустить катящийся в основной сортировщик». Вердикт
`uncertain` отправляет объект на перепроверку, не в основной сортировщик — никаких
тихих пропусков катающихся объектов. Категории:
- `round` — «требует доупаковки» (категория D, если габариты в допуске).
- `not_round` — «подходит для сортировки» (категория B, если габариты в допуске).
- `uncertain` — пограничный случай, оператор или отдельный поток.

Круглость отдельных сечений по-прежнему вычисляется, но **только справочно**
(подсветка сечений в Panel 3): она объясняет форму, но не участвует в вердикте.

### Использование выпуклой оболочки

Оболочка проекции — а не сам (возможно невыпуклый) контур — берётся сознательно:
при качении по плоскости предмет опирается на выпуклую оболочку своей поверхности.
Гантель или катушка (вогнутый профиль) катится так же, как цилиндр по её крайним
дискам — и оболочка это корректно отражает. Это же допущение страховывает G4 от
ложных срабатываний на гантели с круглым стержнем и квадратными торцами: огибающая
проекции вдоль стержня = квадрат, k ≈ 0.707 → отбрасывается.

## Известные ограничения

- **Артефакт конечного числа ракурсов.** Visual Hull тела вращения из 4 ракурсов —
  восьмиугольная призма: k проекции вдоль оси ≤ cos(22.5°) ≈ 0.924 (это же значение
  даёт коробка, повёрнутая на 22.5°, — 4 камеры их не различают). Порог 0.8 оба случая
  проходят; различить их можно только увеличением числа ракурсов (режим Compare
  Configurations показывает эффект).
- **Порог 0.8 — из постановки.** Правильная шестиугольная призма (k = cos 30° ≈ 0.866)
  и куб вдоль пространственной диагонали (правильный шестиугольник в проекции)
  формально проходят порог — это свойство критерия из ТЗ, а не алгоритма. G4
  отбрасывает оба случая: у них k < 0.8 на 6 базовых направлениях, локальный поиск
  также не находит (формы не круглые в строгом смысле) → `uncertain` → оператор.
- **Дискретизация.** Точность оси ограничена шагом локального поиска (5°); k считается
  на растре (субпиксельная растеризация, погрешность < 1 %).
- **Габариты** слегка занижают Y/Z, если экстремум формы попал между сечениями
  (N = 50 даёт погрешность < 1 % на тестовых объектах).
- **Зона неуверенности G4.** Пограничные случаи (k ∈ [0.65, 0.8) после локального
  поиска) уходят в `uncertain` → оператору, не в основной сортировщик. Это сознательное
  решение для логики «лучше перепроверить, чем пропустить катающийся». Доля объектов
  в зоне — ~40% на расширенном тестовом наборе (большинство — коробки, которые
  формально почти-круглые в проекции); в реальном потоке товаров доля зависит от
  ассортимента и может быть ниже.
- **Асимметричные катящиеся с далёкой осью качения.** Если ось качения объекта >30°
  от всех 6 базовых направлений, G4 её не найдёт. На расширенном тестовом наборе
  (11 исходных + 6 синтетических асимметричных) таких объектов не найдено, но это
  ограничение метода, не теоретическая гарантия. `check_model_roll` (полный перебор
  полусферы) оставлен как эталон-оракул для валидации на новых объектах при сомнениях.

**Сводка:**
- 10 уверенных вердиктов (round/not_round), 7 в зоне неуверенности → оператор.
- **0 пропусков катающихся в основной сортировщик** (все 8 реально круглых → round или
  uncertain, ни один не got not_round).
- **1 известный ложноположительный «катится» — `cyl_skewed`** (см. правку 2026-07-31 ниже);
  остальные некруглые — 0 ложных «катится».

Пограничные случаи (важно для отчёта):

- **Короб 400×400×300** — почти куб: проекция вдоль пространственной диагонали —
  шестиугольник (у идеального куба k = cos 30° ≈ 0.866 > 0.8). G4 даёт `uncertain`
  (k=0.754 после локального поиска) → оператор, не в основной сортировщик. У старого
  SCAN-метода это было ложное «катится» (k=0.826).
- **Цилиндр** (гранёный, не тело вращения) — у SCAN ложное «катится» (k=0.807 от
  инфляции Visual Hull); G4 даёт `uncertain` (k=0.756) → оператор.
- **dumbbell** (круглый стержень + квадратные торцы) — физически не катится; G4 даёт
  `uncertain` (k=0.703), отправляет оператору, не в основной.
- **Мешок** — форма близка к скруглённому «мешку-картофелине», k = 0.876: по геометрии
  честно проходит критерий; отнесение мешков к «круглым» — вопрос бизнес-правила,
  а не геометрии.
- **cyl_skewed** (цилиндр + диагональный клин) — **ПРАВКА 2026-07-31 (пользователь,
  визуальный осмотр реальной формы): объект физически НЕ катится** (изначальный эталон
  «round» был ошибочным — см. `config/objects.yaml` в `robozon`, где `cyl_skewed` уже
  давно и правильно стоит `category: ok`, только тестовый набор/документация
  `roboson_tools` не были обновлены под это). Это ЗНАЧИТ, что запись выше — известный
  **ложноположительный** результат G4 (CPU/F1-путь без камерного рига, `num_slices=40`):
  базовые 6 направлений дают k=0.691 (в зоне неуверенности), локальный поиск вокруг
  лучшего из них находит ось с k=0.800 → `round` — но это НЕ настоящая ось переката,
  а артефакт локального поиска, зацепившийся за диагональный клин (тот же класс ошибки,
  что и куб по пространственной диагонали — см. п.2/п.6 «Известные ограничения» —
  только вскрытый локальным поиском, а не базовыми направлениями напрямую). На
  torchhull/GPU-риге (`roboson_tools/core/experiment.py`, задача [[Устойчивая локальная
  круглость вдоль оси переката (G4)]]) этот объект, наоборот, НЕ доходит до `round`
  (k=0.752, uncertain) — расхождение между путями реконструкции, не устранено. Признак
  «устойчивая локальная круглость» (`sustained_fraction`) корректно даёт для найденной
  здесь оси низкое значение (0.083) — т.е. теоретически мог бы поймать и этот
  ложноположительный случай, но включение этой логики для зоны `uncertain` (не только
  `round`) было опробовано и явно НЕ включено в verdict именно из-за более раннего
  (неверного) эталона на этом объекте — см. заметку задачи, требует повторной оценки
  теперь, когда эталон исправлен.
- **asym_barrel** (бочонок + асимметричный край) — F1 даёт k=0.769, локальный поиск
  не находит k≥0.8 (макс 0.794). G4 даёт `uncertain` → оператор. Это пограничный
  случай, который требует ручной проверки.

## Camera Mode — перспективная проекция (параллельный режим просмотра)

Всё выше (силуэты, Visual Hull, круглая проекция) использует **ортографическую** проекцию:
камера считается бесконечно удалённой, силуэт объекта не зависит от его положения вдоль
конвейера (X). Это сознательное упрощение исходного ТЗ: «на уровне математического ядра не
должно существовать понятий камера/объектив/перспектива».

Camera Mode (`silhouette/camera.py`, включается чек-боксом «Проекция (камера FOV,
реалистичные ракурсы)» в GUI) — отдельная, ПАРАЛЛЕЛЬНАЯ возможность посмотреть, как тот же
объект видит реальная камера с конечным фокусным расстоянием:

- **Модель камеры** — идеальный pinhole (rectilinear) без дисторсии и калибровки. Это НЕ то
  же самое, что ортографика: ортографическую проекцию даёт только телецентрическая оптика,
  которая при FOV = 80° физически нереализуема (апертура должна быть ≥ размера объекта).
  Значит перспективные эффекты (разный силуэт объекта в начале/центре/конце кадра по мере
  движения по ленте) — неизбежное следствие геометрии, а не опциональная деталь.
 - **Допущения** — сенсор может быть прямоугольным (`camera_resolution_px: [2592, 1944]` в
   `config/app_settings.yaml`, длинная сторона вдоль ленты; `int` по-прежнему supported как
   квадратный сенсор). FOV `camera_fov_deg` задаётся вдоль ленты (оси строк кадра); поперечный
   FOV получается автоматически из квадратного пикселя. Ось X соответствует вертикали кадра
   (строкам) — та же конвенция, что в Analytical Mode. Ракурсы через зеркало имеют более
   длинный оптический путь (`camera_distance_mm_by_angle`, азимут → реальная дистанция).
   Силуэты строятся субпиксельно (`camera_supersample`): мягкая маска покрытия `coverage`
   [0..1] + субпиксельный контур `contour_px` — граница локализована с точностью ~1/S px.
- **Позиция на ленте** (начало/центр/конец) эмулируется сдвигом объекта вдоль X в пределах
  конуса обзора (`silhouette/camera.belt_offset`), а не реальным перемещением камеры —
  камера в модели неподвижна для заданного азимута θ.
- **Число проекций в Panel 2 равно числу текущих `view_angles`** — как и в ортографической
  сетке, по одному перспективному силуэту на каждый ракурс θ (при фиксированной позиции на
  ленте, выбранной селектором Начало/Центр/Конец); это НЕ дополнительные виртуальные камеры,
  а тот же набор азимутов, что уже используется в Analytical Mode.
- `Silhouette.px_per_unit`/`u_min`/`axis_min` в этом режиме — НОМИНАЛЬНЫЕ (посчитаны на
  референсной глубине `camera_distance`): в отличие от ортографики масштаб перспективной
  проекции не постоянен по кадру, зависит от глубины конкретной точки объекта.

**Voxel carving / polytope hull / exact polyhedral hull остаются визуализацией.** Эти три
3D-реконструкции по перспективным конусам (Panel 1) не участвуют в `dims`/`true_dims`/круглой
проекции ни при каком состоянии чек-бокса — считаются отдельно и только рисуются.

**Габариты/круглая проекция при включённом Camera Mode считаются по перспективным силуэтам.**
`build_silhouette_set` (`core/experiment.py`) — единая точка входа, через которую и `evaluate`
(Panel 3/4), и `check_model_roll` («Проверить модель», `dims`/`true_dims`) получают силуэты.
Чек-бокс «Проекция (камера FOV, реалистичные ракурсы)» переключает эту точку между Analytical
Mode (по умолчанию, ортографика — то, что описано в разделах выше) и Camera Mode (pinhole,
позиция на ленте — тот же `belt_position_combo`, что и для Panel 2/1). `mesh_dims` при этом
всегда остаётся истинным габаритом меша (не зависит от режима силуэтов), поэтому разница
`dims`/`true_dims` от `mesh_dims` с включённым Camera Mode напрямую показывает ошибку
измерения габаритов, которую внесла бы перспектива реальной камеры при заданных
`camera_fov_deg`/`camera_distance_mm` — это и есть назначение чек-бокса, не только просмотр
кадров на Panel 2. Реконструкция (`visual_hull/bands.py`/`reconstruct.py`) при этом работает
неизменной — `Silhouette.px_per_unit`/`u_min`/`axis_min` те же 5 полей независимо от режима
(см. выше), но в Camera Mode они номинальные (посчитаны на референсной глубине), поэтому
band-пересечение по перспективным силуэтам — уже не точная, а приближённая реконструкция
(в отличие от ортографического режима, где оно точное).

### Безопасный запас для start/end (`silhouette/camera.belt_offset`)

`Δx` для start/end подбирается так, чтобы весь объект остался в кадре конечного разрешения —
иначе часть силуэта тихо обрезается по границе кадра и пропадает из всех трёх реконструкций
(voxel carving, polytope hull, exact hull) одинаково, поскольку все три берут маску силуэта из
одного и того же `build_silhouette`.

```
Δx_max = tan(fov/2) · (camera_distance − transverse_radius) · margin_factor − extent_x_from_axis
```

где `extent_x_from_axis` — наибольшее удаление вершины меша от 0 вдоль X (продольная/roll ось),
`transverse_radius` — наибольшее удаление вершины от оси X в поперечной плоскости Y–Z (радиус
объекта, а не его длина), `margin_factor = 0.92` — доля доступного углового бюджета камеры,
реально используемая (запас на растровое округление у самой границы кадра).

**Исправленный баг (обрезание узкой части на start/end).** Прежняя формула
(`Δx_max = camera_distance·tan(fov/2) − extent_x_from_axis·margin_factor`, где `margin_factor`
множил `extent_x_from_axis`) содержала две ошибки:

1. Она считала глубину любой точки объекта равной `camera_distance`, не учитывая, что точки на
   БЛИЖНЕЙ к камере стороне объекта (в пределах его собственного диаметра, `transverse_radius`)
   имеют меньшую глубину и потому проецируются дальше от центра кадра, чем эта линейная оценка
   предполагала. Для объекта с заметным диаметром (не тонкой пластины) это давало реальное
   обрезание по краю кадра на start/end — например, у вертикально стоящей бутылки пропадала
   узкая верхняя часть (горлышко), хотя формально «безопасный» отступ был соблюдён.
2. `margin_factor` был привязан к размеру самого объекта (`extent_x_from_axis`). Для ТОНКИХ
   вытянутых объектов (например, ручка — `extent_x_from_axis` порядка нескольких миллиметров)
   это давало исчезающе малый абсолютный запас (доли процента от углового бюджета камеры) —
   расчёт формально проходил, но растровое округление до целого пикселя всё равно срезало
   объект вплотную к границе.

Исправлено: запас на глубину учтён явно через `transverse_radius`, а `margin_factor` теперь
масштабирует ДОСТУПНЫЙ УГЛОВОЙ БЮДЖЕТ камеры, а не размер объекта — не зависит от того,
насколько объект тонкий. Проверено на 1872 комбинациях (6 STL × шаг yaw 15° × pitch 0/45/90°
× start/end × 4 азимута) — обрезаний по краю кадра не осталось (было 4 из 19 на коробе и почти
всегда на тонкой ручке в узких сценариях). Регрессия —
`tests/test_silhouette_camera.py::test_belt_offset_keeps_object_with_diameter_off_frame_border`
и `::test_belt_offset_keeps_thin_elongated_object_off_frame_border`.

### Voxel carving — 3D-реконструкция по перспективным силуэтам (`visual_hull/voxel_carving.py`)

Чек-бокс «Показать 3D-реконструкцию по проекциям» на Panel 1 — облако точек, восстановленное
carving'ом по кадрам ВСЕХ азимутов текущего набора `view_angles` (как и в Analytical Mode),
для каждого — одна или три позиции на ленте («+ начало/конец ленты»).

**Исправленный баг (раздутая реконструкция).** Изначально carving использовал только ОДИН
азимут (первый угол набора). Один силуэт в принципе не ограничивает объект вдоль оси взгляда
этой камеры — вдоль неё воксели ничем не отсекаются, кроме произвольного запаса вокруг
габарита меша (`margin_ratio`), а несколько позиций на ленте (start/center/end) ситуацию не
меняют — это та же камера, та же ось взгляда. Результат — облако точек, раздутое вдоль этой
оси, визуально сильно асимметричное (замечено пользователем по скриншоту реконструкции короба:
один бок объекта казался значительно меньше другого). Исправлено: carving пересекает силуэты
СО ВСЕХ азимутов набора `view_angles` — тогда каждая ось ограничена хотя бы одной камерой
(нужно минимум 2 взаимно поперечных азимута; см. `tests/test_voxel_carving.py::
test_single_azimuth_is_unbounded_along_view_axis` — контрпример, и `::
test_multiple_azimuths_bound_all_axes` — фикс).

**Почему start/end несут реальную дополнительную информацию, а не тот же кадр со сдвигом.**
В ортографике позиция вдоль ленты не влияет на угол взгляда вовсе. Но под перспективой, когда
объект сдвинут к краю кадра (start/end), лучи от камеры к его точкам идут уже не строго
поперёк продольной оси X, а под углом к ней — камера как бы слегка «заглядывает» с торца.
В кадре проявляется часть торцевой грани объекта, которую центральный кадр (и вся
ортографическая модель) принципиально не видит. Кадры start/center/end одной камеры дают
нетривиально разные силуэты — есть что пересекать (хотя одних их недостаточно — см. выше).

**Почему voxel carving, а не пересечение полигонов (как в `visual_hull/reconstruct.py`).**
Полоса (band) от ортографического силуэта — призма постоянного сечения, поэтому её можно точно
пересекать как 2D-полигон на каждой позиции X. Под перспективой полоса от одного силуэта —
конус/усечённая пирамида: сечение меняется с глубиной, и схема «пересечение 2D-полигонов» не
подходит впрямую (нужна была бы 3D-геометрия пересечения конусов). Voxel carving обходит это
естественно и без новой геометрии: строится 3D-сетка вокселей в габарите объекта (+запас), и
для каждого активного кадра каждый воксель проверяется на попадание в его маску силуэта (та же
проекционная функция, что и в `build_silhouette`, — `project_points`); voxel выживает, если
внутри ВСЕХ активных масок. Пересечение получается автоматически, для любой модели проекции.

**Статус: только визуализация**, не встроено в `dims`/`true_dims`/круглую проекцию — те
по-прежнему считаются исключительно Analytical Mode (band-пересечение по ортографическим
`view_angles`, см. выше). Грубость метода: сетка вокселей (по умолчанию 40³), а не точная
геометрия — облако точек аппроксимирует форму, не восстанавливает её точно; годится для
визуальной оценки "насколько теснее садится реконструкция", а не как источник метрик.

**Исправленный баг (асимметрия).** Растеризация треугольников в `build_silhouette`
использовала `astype(int32)` — усечение к нулю, для положительных пиксельных координат
равносильное floor, а не округлению. Это систематически (ровно на 1px при любом разрешении)
сдвигало силуэт относительно центра кадра. В `analytical.py` того же эффекта нет — там система
координат строится от габарита самого объекта (с явным центрированием), а не от фиксированного
центра кадра. При небольшом объекте в кадре (типично для Camera Mode) 1px давал заметную
мировую асимметрию воксельного облака — исправлено на `np.round(...).astype(int32)`
(см. `tests/test_silhouette_camera.py::test_silhouette_symmetric_for_centered_object`).

Проверка: `tests/test_voxel_carving.py` — реконструкция по одному кадру содержит объект,
добавление start/end может только уменьшать (никогда не увеличивать) число уцелевших вокселей
(инвариант space carving — пересечение), вырожденный случай (объект вне конуса обзора) → `None`.

### Polytope hull — точное пересечение конусов обзора (`visual_hull/polytope_hull.py`)

Альтернатива voxel carving, добавленная для сравнения (независимый чек-бокс «Показать точную
3D-реконструкцию (пересечение конусов)» на Panel 1 — можно включить одновременно с voxel
carving и визуально сравнить оба облака в одной сцене).

**Идея.** Конус обзора одной камеры — пирамида с апексом в камере и основанием, заданным
**выпуклой оболочкой** силуэта (тот же приём, что уже используется для круглой проекции в
`metrics/roundness.py` — оболочка задаёт контакт при перекате, конкретный невыпуклый контур не
важен). Каждая грань такой пирамиды — полупространство (плоскость через апекс и ребро контура).
Форма, видимая одновременно из N камер, лежит в пересечении ВСЕХ этих полупространств —
вычисляется точно через `scipy.spatial.HalfspaceIntersection` (обёртка над qhull), без сеточной
аппроксимации. Нужна интерьерная точка (обычно центроид меша; если он вне пересечения — резервный
план: центр Чебышева через `scipy.optimize.linprog`).

**Сравнение с voxel carving:**
- **Точнее** — точный выпуклый многогранник, а не блочная сетка вокселей.
- **Дешевле вычислительно** — пересечение нескольких десятков полупространств вместо проверки
  десятков тысяч вокселей.
- **Та же оговорка**, что и у voxel carving/круглой проекции: даёт именно ВЫПУКЛУЮ оболочку
  формы — для вогнутого объекта это переоценка (как и любой Visual Hull). На практике не
  просто «переоценка объёма»: резкий уступ (толстая зажимаемая часть → тонкий стержень у
  ручки) реконструируется как плавный конус, а не цилиндр с уступом — контур силуэта
  выпрямляется в `cv2.convexHull` ещё до построения полупространств, поэтому вогнутость стирается
  безвозвратно. См. ниже Exact Polyhedral Visual Hull — метод БЕЗ этого допущения.
- **То же требование к азимутам**: одного азимута недостаточно — полупространства одного конуса
  неограничены вдоль оси взгляда, `HalfspaceIntersection` не может построить конечный
  многогранник → метод возвращает `None` (не приближённо раздутую форму, как было бы у voxel
  carving на грубой сетке, а честный отказ).

На коробе 200×100×60, 4 азимута (0/45/90/135): выпуклый многогранник ~106×104×65 (истина
200×100×60, наблюдаемое расхождение — тот же артефакт конечного числа ракурсов, что уже
описан выше для круглой проекции), объём ~1.29M против истинных 1.2M мм³ (+7.5%,
согласуется с ожидаемой инфляцией Visual Hull от 4 ракурсов).

**Асимметричный «выступ» на почти-кубе — свойство набора ракурсов, не баг геометрии конуса.**
На коробе, близком к кубу (например, «Короб 400×400×300»), реконструкция заметно приподнята
над одним рёбрам сильнее, чем над симметричным ему — по скриншоту выглядит как асимметрия
самого метода. Проверено: математика одного конуса зеркально точна (полупространства для
зеркальных азимутов `+θ`/`−θ` совпадают с точностью до порядка обхода контура, см.
`test_polytope_hull.py::test_mirrored_azimuths_give_mirrored_halfspaces`). Причина — дефолтный
набор ракурсов рига «2 камеры + 1 зеркало» `[0°, 45°, 90°, 135°]`: 135° охвата в ОДНУ сторону,
без зеркальной пары почти ни для одного угла. Полный симметричный набор (8 углов по кругу) даёт
побитово одинаковый избыток объёма по обе стороны каждой оси — см.
`test_asymmetric_default_views_give_asymmetric_bulge`. Не исправлено намеренно (решение
пользователя, 2026-07-10) — набор ракурсов задан физическим ригом, а не выбором алгоритма.

Проверка: `tests/test_polytope_hull.py` — один азимут → `None`; 4 азимута дают многогранник с
габаритом и объёмом, близкими к истинным (в пределах ожидаемого артефакта); добавление кадров
может только уменьшать объём (никогда не увеличивать — инвариант пересечения полупространств);
вырожденный случай → `None`.

**Новая зависимость:** `scipy` (добавлена в `requirements.txt` специально для
`HalfspaceIntersection`/`linprog`) — устойчивая библиотека без GUI/рендер-зависимостей, в
отличие от отклонённых ранее вариантов (`trimesh.Scene`+pyglet, `trimesh.boolean` с внешними
движками) — см. заметку задачи, раздел про рассмотренные и отклонённые библиотеки.

### Exact Polyhedral Visual Hull — точное пересечение НЕвыпуклых конусов (`visual_hull/exact_polyhedral_hull.py`)

Третий, независимый чек-бокс на Panel 1 («Показать точную 3D-реконструкцию (невыпуклая, exact
polyhedral hull)») — метод Franco & Boyer, "Exact Polyhedral Visual Hull" (2003), решающий
ограничение polytope hull напрямую: сохраняет вогнутости силуэта вместо того, чтобы стирать их
через `cv2.convexHull`.

**Идея.** Конус обзора одной камеры строится не как пирамида по выпуклой оболочке контура, а
как замкнутый треугольный меш («апекс + дальняя крышка на глубине `far_distance`»), где крышка
триангулирована ear-clipping'ом (`trimesh.creation.triangulate_polygon`, движок `mapbox_earcut`)
по РЕАЛЬНОМУ (возможно невыпуклому) контуру силуэта, а боковая поверхность — веер треугольников
апекс-ребро. Пересечение таких тел по всем ракурсам — булева 3D-операция
(`trimesh.boolean.intersection`, движок `manifold3d`), а не пересечение полупространств: результат
может быть НЕвыпуклым.

**Проверка на выпуклом объекте.** На коробе даёт результат, совпадающий с polytope hull в
пределах ±2% по габаритам и объёму — ожидаемо, поскольку выпуклая оболочка выпуклого контура не
меняет его форму (`test_exact_polyhedral_hull.py::test_convex_object_matches_polytope_hull`).

**Проверка на невыпуклом объекте.** Синтетический ступенчатый стержень (два соосных цилиндра
разного радиуса встык — аналог ручки) реконструируется exact-методом с почти плоским профилем
радиуса на каждом цилиндрическом участке (разброс < 2 мм), тогда как polytope hull даёт
монотонный линейный скат (разброс > 8 мм) — воспроизводит и чинит баг с «конусом вместо
цилиндра» на реальной «Ручка.stl»: на месте, где нет зажима, exact-метод восстанавливает радиус
с точностью 0.3–4% от истинного, тогда как polytope hull завышает его на 40–80%
(`test_exact_polyhedral_hull.py::test_stepped_rod_preserves_shoulder_polytope_hull_does_not`).

**Исправленный баг (тихий отказ на некоторых ракурсах/поворотах).**
`trimesh.creation.triangulate_polygon` возвращает вершины кольца контура КАК ЕСТЬ, включая
точку-дубликат первой (шейпли хранит кольцо замкнутым); earcut эту дублирующую вершину в
`cap_faces` не использует, но при сопоставлении границы конуса с вершинами крышки через
`cKDTree` с нулевым допуском поиск иногда попадал на ДРУГОЙ индекс той же геометрической точки,
чем использует `cap_faces`. Крышка и боковой веер оказывались «сшиты» по разным индексам одной
точки — меш переставал быть 2-многообразием, и `carve()` тихо возвращал `None` (реконструкция
просто не появлялась, без ошибки). Проявлялось не на каждом контуре, поэтому ловилось через раз
на коробе (4 из 19 углов) и почти всегда — на сложном контуре шлема. Исправлено дедупликацией
вершин крышки (`np.unique` по округлённым координатам) до сопоставления границы. Регрессия —
`test_exact_polyhedral_hull.py::test_stable_across_yaw_sweep` (плотный перебор yaw 0–180°).

**Грабли рендера (не в расчёте, в GUI).** Два полупрозрачных `GLMeshItem`
(`glOptions="translucent"`) без ручной сортировки back-to-front гасят друг друга через тест
глубины OpenGL — если polytope- и exact-халл почти совпадают (выпуклый объект), второй
отрисованный слой был ПОЛНОСТЬЮ невидим независимо от корректности расчёта. Исправлено
переключением обоих сравниваемых халлов на `glOptions="additive"` (тест глубины не
используется, порядок отрисовки не важен) и добавлением чек-бокса «Показывать сам объект
(сплошной меш)» (`model_panel.set_object_visible`) — halls, почти совпадающие с поверхностью
объекта, иначе полностью скрыты его непрозрачным мешем.

**Новые зависимости:** `manifold3d` (булевы операции над мешами) и `mapbox_earcut`
(триангуляция невыпуклого контура) — добавлены в `requirements.txt`, ставятся как готовые
wheel-пакеты (win_amd64/cp312), компилятор не нужен.

Проверка: `tests/test_exact_polyhedral_hull.py` — вырожденный случай (< 2 ракурсов) → `None`,
совпадение с polytope hull на выпуклом объекте, сохранение уступа на ступенчатом стержне,
устойчивость к повороту (плотный перебор yaw), + стресс-тест на 36 комбинациях
